# **2\. Поднятые сервисы — и почему именно они**

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Локальная легковесная альтернатива AWS S3. Полностью совместим с S3 API, быстро разворачивается локально. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Обеспечивает строгие ACID-гарантии для хранения состояния метаданных каталога. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует открытый стандарт REST Catalog. Позволяет разным движкам (Trino, Spark) безопасно работать с одними таблицами без конфликтов. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | MPP-движок для интерактивной ad-hoc аналитики. Выполняет быстрые SQL-запросы без накладных расходов на инициализацию JVM. |
| Apache Superset | отчёт/дашборд поверх Gold | Нативный, легковесный open-source BI-инструмент. Работает с Trino "из коробки", что позволяет строить дашборды напрямую из Iceberg. |

      \- MINIO\_ROOT\_USER=admin

  postgres:

    image: postgres:15

    environment:

      \- POSTGRES\_USER=lakekeeper

      \- POSTGRES\_PASSWORD=lakekeeper

      \- POSTGRES\_DB=lakekeeper

    ports:

      \- "5432:5432"

  lakekeeper:

    image: lakekeeper/lakekeeper:latest

    environment:

      \- DB\_URL=postgres://lakekeeper:lakekeeper@postgres:5432/lakekeeper

      \- S3\_ENDPOINT=http\://minio:9000

      \- S3\_ACCESS\_KEY=admin

      \- S3\_SECRET\_KEY=password

    ports:

      \- "8181:8181"

    depends\_on:

      \- postgres

      \- minio

  trino:

    image: trinodb/trino

    ports:

      \- "8080:8080"

    volumes:

      \- ./trino/catalog:/etc/trino/catalog

    depends\_on:

      \- lakekeeper

# **3\. Разбор запроса — какие данные нужны**

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :---- | :---- | :---- |
| customer | c\_custkey, c\_name | c\_custkey — джойн с заказами. c\_name — вывод в результат и группировка (GROUP BY). |
| orders | o\_orderkey, o\_custkey, o\_orderdate, o\_totalprice | o\_orderkey — джойн с позициями. o\_custkey — джойн с клиентами. Остальные для вывода и сортировки. |
| lineitem | l\_orderkey, l\_quantity | l\_orderkey — джойн с заказами. l\_quantity — фильтр (HAVING SUM \> 300\) и агрегация (SUM). |

# **6\. Часть 2 — осмысление и работа с инструментами**

## **6.1. Понять и объяснить**

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычные СУБД жестко связывают хранение и вычисления, что дорого масштабировать. Lakehouse разделяет эти слои: данные лежат в дешевом S3 в открытых форматах (Parquet), а метаданные (Iceberg) обеспечивают ACID-транзакции. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В Iceberg изменение схемы \= изменение метаданных, а не файлов. При добавлении колонки Iceberg обновил метаданные (записал новую схему в манифест), не перезаписывая старые файлы. Новые файлы будут писаться с новой колонкой, а при чтении старых файлов Iceberg вернет NULL. |
| Пример скрипта восстановления данных из снапшота (time travel) | `SELECT * FROM bronze.lakehouse.raw_customer FOR VERSION AS OF 128504289547937565 WHERE c_custkey = 999999;` |

# **7\. Выводы**

Архитектура Lakehouse решает проблему вендор-лока и жесткой связи хранения с вычислениями. Использование табличного формата Apache Iceberg поверх S3-хранилища MinIO позволило реализовать транзакционность, schema evolution и time travel. Применение колоночного формата Parquet в связке с алгоритмами сжатия в зависимости от слоя (GZIP для Bronze, ZSTD для Silver, Snappy для Gold) обеспечило оптимизацию ресурсов. Многослойная модель "Медальон" упростила создание пайплайнов, позволив применять историчность (SCD Type 2\) на уровне Silver, формируя готовые агрегаты для бизнеса на уровне Gold.
