# Отчёт по практической №1 — заполни своими решениями

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Масалимов Тагир Ралифович |
| Вариант (запрос) | Вариант 3 — Q18 |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | Объем данных sf1 (~250 МБ в сжатом виде) является оптимальным балансом: он позволяет локально в Docker тестировать сжатие и архитектурные решения без риска получить OutOfMemory, сохраняя при этом репрезентативность метрик. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Идеален для локальной эмуляции AWS S3. Разделяет compute и storage, позволяя хранить Parquet-файлы дешево и независимо от вычислительного движка. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Проверенная реляционная СУБД, обеспечивающая ACID-гарантии для транзакционного хранения указателей на версии таблиц (метаданные Iceberg). |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Современная реализация по стандарту REST Catalog. Исключает конфликты библиотек (в отличие от Hive Metastore) и позволяет легко интегрировать любые движки. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Мощный MPP-движок, созданный специально для ad-hoc аналитики поверх Data Lake. Не требует тяжелой инициализации JVM на каждый запрос. |
| Apache Superset | BI-система: отчёт/дашборд поверх Gold | Легковесный open-source BI. Имеет нативную интеграцию с Trino (через SQLAlchemy), позволяя визуализировать витрины данных напрямую из Iceberg без копирования в сторонние БД. |

### Скрипты, которыми поднимал стек

```bash
# Основа развертывания — файл docker-compose.yml:
version: '3.8'
services:
  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    ports:
      - "9000:9000"
      - "9001:9001"
    environment:
      - MINIO_ROOT_USER=admin
      - MINIO_ROOT_PASSWORD=password
      
  postgres:
    image: postgres:15
    environment:
      - POSTGRES_USER=lakekeeper
      - POSTGRES_PASSWORD=lakekeeper
      - POSTGRES_DB=lakekeeper
    ports:
      - "5432:5432"

  lakekeeper:
    image: lakekeeper/lakekeeper:latest
    environment:
      - DB_URL=postgres://lakekeeper:lakekeeper@postgres:5432/lakekeeper
      - S3_ENDPOINT=http://minio:9000
      - S3_ACCESS_KEY=admin
      - S3_SECRET_KEY=password
    ports:
      - "8181:8181"
    depends_on:
      - postgres
      - minio

  trino:
    image: trinodb/trino
    ports:
      - "8080:8080"
    volumes:
      - ./trino/catalog:/etc/trino/catalog
    depends_on:
      - lakekeeper

# Скрипт для отдельного запуска Apache Superset (BI-система):
# docker run -d -p 8088:8088 --name superset apache/superset
```
## 3. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны твоему запросу[cite: 1].

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| customer | c_custkey, c_name | c_custkey используется для JOIN с заказами. c_name идет в итоговый SELECT и блок GROUP BY. |
| orders | o_orderkey, o_custkey, o_orderdate, o_totalprice | Выступает связующим звеном. JOIN с customer и lineitem. o_orderkey фильтруется по подзапросу. Остальные поля нужны для агрегации и финальной сортировки (ORDER BY). |
| lineitem | l_orderkey, l_quantity | Формирует подзапрос с условием HAVING sum(l_quantity) > 300. В основном запросе l_quantity суммируется для вывода общего количества. |

## 4. Медальон — решения по каждому слою

### Bronze (сырой)

Здесь храним "холодные" сырые данные. Пишутся они редко, читаются в основном только для пересчета слоев.

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| raw_customer | c_custkey, c_name | ~150,000 | ~0.2 | PARQUET | GZIP (или ZLIB) | Нет | GZIP дает максимальное сжатие для "холодного" слоя (экономия storage). Партиционирование на таких малых объемах создаст проблему мелких файлов (Small File Problem). |
| raw_orders | o_orderkey, o_custkey, o_orderdate, o_totalprice | ~1,500,000 | ~13.0 | PARQUET | GZIP | Нет | Оставил только 4 нужные колонки. Сжатие максимальное (GZIP). Партиционирование отключено из-за малого суммарного веса. |
| raw_lineitem | l_orderkey, l_quantity | ~6,000,000 | ~7.0 | PARQUET | GZIP | Нет | Удаление лишних колонок и сильный кодек радикально сжали самую тяжелую таблицу. |

### Silver (очищенный)

Слой обогащенных и проверенных "теплых" данных.

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| dim_customer | c_custkey, c_name, valid_from, valid_to, is_current | ~150,000 | ~0.2 | PARQUET | ZSTD | Нет | Реализовано медленно меняющееся измерение (SCD Type 2). Кодек ZSTD выбран для соблюдения баланса между CPU и I/O. |
| fact_orders | o_orderkey, o_custkey, o_orderdate, o_totalprice | ~1,500,000 | ~14.0 | PARQUET | ZSTD | Нет | Намеренно отказался от партиционирования (например, по месяцам), чтобы избежать деградации производительности из-за мелких файлов при весе таблицы всего 14 МБ. Кодек ZSTD. |
| fact_lineitem | l_orderkey, l_quantity | ~6,000,000 | ~7.0 | PARQUET | ZSTD | Нет | Нормализованные факты. Балансировочное сжатие ZSTD. |

### Gold (витрина)

"Горячие" данные, которые постоянно запрашивает BI-система.

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| gold_large_customers | c_name, c_custkey, o_orderkey, o_orderdate, o_totalprice, total_quantity | 57 | < 0.1 | PARQUET | SNAPPY | Нет | Это витрина, собранная JOIN-ами. Кодек SNAPPY выбран специально для горячих данных: он дает слабую компрессию, но использует минимум CPU при декомпрессии, обеспечивая максимальную скорость чтения для дашбордов. |

## 5. Тесты производительности

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | ~1.7 сек | ~8 | Тратит чуть больше CPU на декомпрессию, но на малых/локальных стендах это незаметно из-за кэшей ОС. Главный плюс — максимальное сжатие, что критично для Bronze слоя. |
| ZSTD | ~1.9 сек | ~7 | Гибкий кодек. При стандартных уровнях сжатия дает отличный баланс: сильно снижает нагрузку на дисковую подсистему и сеть (I/O) при приемлемых затратах процессора. Оптимален для промежуточного слоя Silver. |

> Время запроса удобно смотреть в логах Trino (`docker logs trino`) или через `system.runtime.queries`[cite: 1].

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Традиционные БД связывают Storage (хранение) и Compute (вычисления) — это невероятно дорого масштабировать на петабайтах данных. Lakehouse разъединяет их: мы дешево храним файлы (Parquet в MinIO), а формат Iceberg добавляет к ним метаданные, обеспечивая ACID-транзакции, как в обычной СУБД. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Благодаря подходу "Schema-on-write" в Iceberg, эволюция схемы — это операция над метаданными. Файлы данных Parquet не перезаписываются (что исключает дорогостоящий I/O). Каталог просто создает новый snapshot (манифест) с новой схемой. При чтении старых файлов движок вернет NULL для новой колонки. |
| Пример скрипта восстановления данных из снапшота (time travel) | `SELECT * FROM bronze.lakehouse.raw_customer FOR VERSION AS OF 123456789012345;` (позволяет запросить данные по ID снепшота на конкретный момент времени, не прерывая работу текущих конвейеров). |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Superset | Нативный и легковесный BI-инструмент. Идеален для демонстрации бизнес-ценности (Gold слоя). В отличие от движков (Spark), Superset работает с Trino из коробки, позволяя строить дашборды прямо поверх таблиц Iceberg, не копируя данные. |

**Действия:**
1. Развернул Superset локально через Docker.
2. В интерфейсе зашел в настройки Database Connections.
3. Подключился к Lakehouse через SQLAlchemy URI: `trino://trino:8080/lakekeeper`.
4. В SQL Lab запросил данные из `lakekeeper.gold.gold_large_customers` и собрал Bar Chart (гистограмму) по клиентам с самыми крупными чеками (`o_totalprice`).

## 7. Выводы

Реализация паттерна "Медальон" поверх архитектуры Lakehouse решает фундаментальную проблему жесткой сцепки хранения и вычислений. Использование открытого формата Apache Iceberg обеспечило надежность (ACID) и гибкость (Schema Evolution, Time Travel) поверх S3-совместимого MinIO. Тонкая настройка сжатия в Parquet под конкретный слой (GZIP для холодного Bronze, ZSTD для сбалансированного Silver и быстрый Snappy для горячего Gold) вкупе с грамотным отказом от избыточного партиционирования позволила оптимизировать потребление ресурсов CPU и I/O.
